# OPTICAL WEATHER v4.1 — content management

## Decision

OPTICAL WEATHER remains a static GitHub Pages site. v4.1 does **not** introduce a public community-submission system, database, SaaS CMS, account layer, API key, or backend.

The requirement is simpler: make ongoing **in-house curation** easy enough that new playlists, programmes and editorial corrections do not require editing application logic.

## Content model

The existing v3 catalogue remains the canonical historical base:

- `data-ready.js`
- `data-1.js`–`data-4.js`
- `metadata-v2.js`

v4.1 adds:

- `content/curation.js` — the human-editable editorial layer;
- `content/registry.js` — validation, deterministic merging and assembled collection counts before `app.js` starts;
- `tests/content-management.test.mjs` — overlay and validation tests;
- `.github/workflows/test.yml` — automatic Node test runs on feature pushes and pull requests.

This keeps the public site backwards-compatible while allowing new work to be commissioned and added in one controlled place.

## Editorial workflow

1. Add a ready-made playlist or programme to `content/curation.js`.
2. Preserve a precise `Find current copy` YouTube search for each programme item, even when a direct watch link exists.
3. Add a matching `metadata.programmes` entry for every new programme id.
4. Add access/editorial claims only when they have actually been checked. Do not infer captions, subtitles, intertitles, language or sensory characteristics from titles or search results.
5. Run `npm test` and require CI to pass.
6. Preview desktop and narrow mobile widths.
7. Review the editorial change through the normal Git branch/PR flow before publication.

## Validation and replacement rules

The merge layer is intentionally conservative and fails loudly on malformed additions.

- ready-made streams are keyed by exact `title`;
- duplicate ready-made titles inside the curation layer are rejected;
- programmes are keyed by the two-digit id at the start of `title` (`01`–`99`);
- duplicate programme ids inside the curation layer are rejected;
- every programme requires a description, duration, tags, items and modes;
- every programme item requires title, credit, runtime and a resilient YouTube search fallback;
- a new programme id requires a matching metadata entry;
- programme metadata is merged by programme id;
- the final assembled catalogue is rejected if programme ids are missing or duplicated.

An entry with an existing valid key replaces that historical entry. A new valid key appends it. No fuzzy matching occurs.

## Collection counts

Programme and route totals shown in the public footer are derived from the assembled catalogue after the curation layer is merged. New programmes therefore cannot leave stale hard-coded `36 programmes / 267 routes` copy behind.

The static social description deliberately avoids numerical collection claims because social crawlers generally do not execute the client-side catalogue assembly.

## Why this is v4.1 rather than a heavy CMS

The collection is curated, comparatively small and editorially sensitive. A server CMS would add authentication, persistence, deployment and security complexity without improving the public experience. The static curation layer preserves the site's portability and allows the collection to grow without coupling content updates to UI code.

## Future migration

If the catalogue grows far beyond the current scale, the same editorial schema can later move to JSON/YAML or a headless CMS. That migration should happen because the editorial workload justifies it, not because a CMS is fashionable.
